Import tickets

RT tickets are routine team-handled work, not ITIL incidents, so each one that hasn't already been imported becomes a new "IT operations events" record (type "RT Ticket"), not an Incident — except a ticket whose Subject contains the tag "[CR]" (case-insensitive), which imports as a ServiceOps Change instead, since that's this org's convention for a change request. Historical changes are inserted as already-decided records (no CCB/approval tasks are spun up for them — those already happened in RT). RT Queue maps to an owning team (matched by name, or created if none matches — same as CSV CMDB import resolves team names), RT Requestor/Owner map to ServiceOps users by email (auto-created if not found), and RT Status/Priority map to the closest ServiceOps equivalent (an unrecognized status is reported as an error rather than silently guessed). Every correspondence message, status change, and file-attachment filename (the file itself isn't imported, just its name) from RT's full history is folded into the description as a dated log, in order. The RT ticket number is kept as a "Source ticket #" (events) or shown in history (changes) and is searchable from the relevant list's search box. A ticket already imported (matched by its RT ticket ID, wherever it landed) is always skipped, never duplicated — safe to re-run after fixing a mapping problem, though a record already imported won't be retroactively corrected by a later re-run; fix it by hand or delete and re-import it. Run a preview first and check the sample rows below before applying anything. RT is not modified in any way — this only reads from it.
