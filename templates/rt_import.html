Import tickets

RT tickets import as "IT operations events" (not Incidents), except a "[CR]"-tagged Subject, which imports as a Change instead. Run a preview first and check the sample rows below before applying anything. RT is not modified in any way — this only reads from it.

How mapping, attachments, and re-runs work

RT Queue maps to an owning team (matched by name, or created if none matches). RT Requestor/Owner map to ServiceOps users by email (auto-created if not found); a ticket whose Requestor has no usable email is credited to a placeholder "RT Import (unresolved requester)" account rather than to whoever ran the import. RT Status/Priority map to the closest ServiceOps equivalent — an unrecognized status is reported as an error rather than silently guessed. Every correspondence message, status change, and file attachment from RT's full history is imported, in order: messages and status changes as a dated log folded into the description, and attachments as real downloadable files (subject to the same file-type allowlist and malware scan a normal upload gets — a rejected one is still noted by filename in the description log). The RT ticket number is kept as a "Source ticket #" and is searchable from the relevant list's search box. A ticket already imported (matched by its RT ticket ID) is always skipped, never duplicated — safe to re-run after fixing a mapping problem, though an already-imported record won't be retroactively corrected by a later re-run; fix it by hand or delete and re-import it. Historical changes are inserted as already-decided records — no CCB/approval tasks are spun up for them, since those already happened in RT.
